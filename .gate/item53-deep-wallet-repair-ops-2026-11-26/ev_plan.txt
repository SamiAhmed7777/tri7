## The command

Run by hand, once, right after a timer catch-up has finished so that it does
not overlap the next one:

    /root/tri7/target/release/addrindex_build /var/lib/tri7/blk0001.dat /var/lib/tri7 --deep-wallet-repair=apply

## What it writes

One SQLite transaction, wallet-address rows of addressindex.db only:

- 218 output rows whose transaction is in no canonical block: deleted
- 225 spend markings (spent_height) set from the orphan block's height to
  the canonical block that spends the coin
- 159 history rows (tx_addr) of the orphaned transactions: deleted;
  1 history row written

Nothing else: no chain data, no wallet file, no key material, no
balances.json, no other addresses' rows. The wallet file is opened with the
node's own wallet reader and only its key addresses are used; nothing from
it is printed or written. The ordinary window verify and the tail catch-up
then run exactly as in every timer run.

## Guards on the write (in the committed, graded code)

- a dry run unless `=apply` is on the command line
- rows are re-read inside the write transaction and written only if they
  are still what the snapshot saw; anything else is counted `raced` and
  left alone
- the tipstate oracle is read again right before the transaction; a
  changed window aborts (exit 3) with nothing written

## Expected after the apply

The run's own before and after must differ by exactly the phantom rows:
after = before − 218 rows and − 3581.961062 TRI. In the dry run that was
383 rows / 5170.155950 TRI -> 165 rows / 1588.194888 TRI. New stakes land
while all this runs (listunspent had 397 rows at 09:20 PST), so the absolute
count at apply time is higher than 165; the difference is what must match.
Every remaining row is in the canonical block at its height.

## Rollback — a script, tested; not a paragraph

`item53_rollback.sh` (sha256 eeb6bc5e7509d29fd9f4880c177b296ce46461d484c3f6e1bc8ec9d5f0d21c83)
restores the backup and proves it:

1. Preconditions, before anything is touched: the backup hashes to its
   pinned sha256, the three units exist, every command exists, at least the
   backup's size plus 1 GiB is free. A failed precondition is exit 1 with
   nothing touched.
2. The restored file is prepared next to the live one and hash-verified —
   still nothing live touched.
3. Stop the timer, let a running catch-up finish, stop the daemon.
4. Remove the WAL sidecars, rename the prepared file into place, set the
   original owner and mode, and hash it again.
5. Start the daemon, wait (bounded) for its RPC, start the timer, run one
   catch-up, require Result=success.

Exit 0 only when all of that held. Exit 2 names the step that failed,
prints the units' states and the free space, and leaves the services as
they are. Every step logs the free space of the index's disk. `--check`
prints the three units' states at exit and stops none of them — the timer
keeps running, so a catch-up may legitimately be active there.

Evidence: 37 sandbox checks over ten scenarios and six mutants each caught
by its expected checks (ev_rollback_sandbox.txt, ev_rollback_mutants.txt);
the `--check` half run on this host against the real backup — prepared copy
verified, nothing stopped (ev_rollback_check_live.txt).

Cost: the applied index is kept beside the restored one as a hard link (no
extra space); the prepared copy adds 1473306624 bytes until it is renamed.
The daemon is down for the swap — seconds — plus its own start time.

Not done for real: the swap itself has never run on the live host. Only its
pre-swap half (`--check`) and the sandbox have.

## Known limits, stated rather than hidden

- The rollback snapshot is from before the dry run (08:19-08:21 PST); the
  apply comes later. A rollback replays that gap; it loses no chain data.
- The daemon keeps writing the index while the repair runs. Rows it changes
  after the repair's snapshot are left alone (raced), never overwritten.
- A reorg BELOW the vouchable window during the run is not detected: the
  oracle vouches for the window only.
- The backup is on the same disk as the index (the only disk, 97% full). It
  protects against a bad write, not against a disk failure.
- Rolling back stops the staking daemon for the length of the swap. That is
  the cost of the safety net, not a step of the plan.
- This corrects the item's E5 reading. Those 225 coins are not unspent coins
  hidden from the list: the canonical chain spends every one of them, 3 to
  175 blocks after the orphan block. Nothing returns to unspent, and the
  listed balance falls by exactly the phantom rows' value.

## Not in this step

Pi and DNS3 (no address index there); F3; any wallet file or key operation.

## Revision notes — 2026-11-27, item 54 parts C and D

Appended after the apply. The sections above are the text that was graded and
run on 2026-11-26; they are left as they were.

- **CATCHUP_WAIT** is 600 s by default (`ITEM53_CATCHUP_WAIT`). It is how long
  the rollback waits for a running catch-up to end, and that wait comes BEFORE
  the daemon is stopped: the timer is stopped, the catch-up is left to finish,
  and only then is the daemon stopped. So a rollback can hold the timer stopped
  for up to ten minutes with the daemon still staking, and it fails (exit 2,
  nothing swapped) if the catch-up has not ended by then.
- **The owner and mode of the restored index are now fatal to get right.**
  After the swap the rollback used to run `chown` and `chmod` with `|| true`,
  so a failed chown would have left the index with the wrong owner while the
  script went on to print "ROLLBACK DONE AND PROVEN". It now stops with exit 2
  and prints the commands that set them by hand (sandbox cases K and L;
  mutants `chown_failure_ignored`, `chmod_failure_ignored`).
- **The fault injection is test-only by construction.** `ITEM53_SANDBOX=1`
  with `ITEM53_TEST_FAULT=<name>` is the sandbox harness's. The script used to
  say the live default path refuses it, which was not true for `post_swap_sha`.
  It now refuses the run before the lock is taken whenever that is asked for
  on the live index path (sandbox case M; mutant `live_path_guard_removed`;
  demonstrated on DNS2 itself in ev_rollback_live_refusals_r3.txt).
- **V2's per-address check** (item53_after_check.py, unchanged) assumes the
  index stores addresses in the same string form listunspent returns. A format
  mismatch would show there as a FAIL, the safe direction.
- **The backup this plan made is being deleted** as part D of item 54
  (2026-11-27), under its own grade: BRIEF_r3_polish_cleanup.md puts that
  deletion to the judge together with the script revision above, and
  ev_backup_cleanup.txt is its record.
  `/root/tri7-lab/backups/item53-pre-dryrun-2026-11-26T0819` held five files,
  1,478,447,797 bytes. The repair it protected has been the live index
  since 2026-11-26T09:43 PST, and the snapshot held h2220359 with the phantom
  rows still in it: it was not a state to return to. `item53_rollback.sh`
  now refuses with "no backup at ..." unless `ITEM53_BACKUP_DIR` and
  `ITEM53_BACKUP_SHA256` name another verified copy.

The sandbox and its mutants are kept beside the script now
(item53_rollback_sandbox.sh, item53_rollback_mutants.sh); on 2026-11-26 they
lived in a scratch directory. Evidence of this revision:
ev_rollback_sandbox_r2.txt (51 checks), ev_rollback_mutants_r2.txt (9 mutants).
